# AI 陪伴引擎 · 参考实现

> **一个带知识边界和双轴情感引擎的 AI 人格框架 ——
> 让角色知道自己该知道什么，并对此有真实的情绪反应。**

纯前端、零构建、无后端，**可运行的参考实现**（不是架构图，是能跑起来、有测试的那种）。
重点不是"接个大模型"，而是"怎么让她像个人"。

界面故意做成微信的样子（气泡、连发、时间分隔、正在输入）——
因为要验证的东西只有当它看起来像"手机里一个真实的人"时才测得出来。

```
你说一句话
   │
   ├─ 记忆：她记得住吗？很久以前的事翻得出来吗？该忘的忘掉了吗？
   ├─ 时间：她知道现在几点、隔了多久、你说的"明天"还有多远吗？
   ├─ 关系：她认同自己的身份吗？会不会演着演着就串了？
   ├─ 情绪：她是暖的还是冷的？情绪有起伏吗？还是每句一个温度？
   └─ 边界：她不懂的东西会不会装懂？不懂你的事会不会连你一起推开？
```

## 快速了解（三分钟版）

**这是什么**：一套**提示词工程 + 状态管理**的做法，用来让一个 LLM 扮演长期角色时不崩。
不含任何模型 —— 你自己带 API Key（或本地 llm.cpp），它负责"她该记得什么、该懂什么、
该怎么变"。

**技术栈**：纯浏览器端 ES Module + localStorage。**运行时零依赖**，
`npm install` 只是为了装测试用的 jsdom。没有构建步骤，没有后端，没有数据库。

**最该看的两份东西**：
1. [二、与同类项目的区别](#二与同类项目的区别) —— 三行说清它和别人的定位差异
2. [四、核心设计取舍](#四核心设计取舍) —— 11 条"为什么这么设计"，每条都写了踩过的坑

**如果只看一件事**：打开 [`src/memory.js`](src/memory.js) —— **173 行，遗忘曲线的全部实现**
（复习次数 → 半衰期 → 什么时候该忘、什么永远不会忘），零依赖、可单独 import。
看完那 173 行你就知道这个项目的成色了。

**想直接跑**：见 [五、跑起来](#五跑起来)，两条命令。

### 这个项目适合谁

- 你在做 AI 角色 / 陪聊 / 桌宠 / NPC，**已经被"她怎么又忘了""她怎么什么都懂"折磨过**
- 你想看的是**设计取舍和它们的理由**，不是又一份"接 OpenAI SDK"的样板
- 你需要在**提示词层**加东西，而不是换一个推理框架（模型/记忆存储/推理后端都可以照旧）
- 你要一份**读得完、跑得起来、有测试**的参考，来抄某一层（比如只想要遗忘曲线的做法）
- 手机端 / 纯静态部署 / 不想要后端 —— 这个项目就是为这个形态做的

### 这个项目不适合谁

- 你要的是**开箱即用的成品 App**：这里没有账号体系、没有云端同步、没有后台管理
- 你要**多租户 / 服务端存储 / 大规模语料**：存储是浏览器 localStorage，
  检索是 2/3-gram + IDF，天花板就在那儿（刻意的，见 [取舍 6](#6-检索用-idf-而不是向量)）
- 你要**生产级的安全与审计**：记忆存在用户自己的浏览器里，删了就没了，
  没有多人权限、没有审计日志
- 你想**训练 / 微调模型**：这里一行训练代码都没有，全是提示词与状态
- 你只是想要一份**大而全的 agent 框架**：这个仓库很小，只解决"人格连续性"这一件事

### What / Why (English)

**What.** A pure-frontend reference implementation of a long-lived AI persona engine:
memory with decay, a virtual clock, relationship-vs-affection as two orthogonal axes,
real-time mood, and an explicit *knowledge boundary*
(a character that knows what someone of its age and job would know — and admits when it doesn't).
No model, no server, no build step; bring your own API key.

**Why.** Most "AI companion" projects fail not because the model is weak, but because
the persona has *structural* defects: it forgets, it remembers things it shouldn't,
its emotions are flat, its identity drifts, and it either fakes expertise or shuts the
user out. Those defects fight each other — fixing "relationship is fixed" breaks
"affection changes" unless you separate the two axes first.
This repo is the working record of taking those defects one at a time, with the reasoning
and the counter-examples kept in the code comments and in the tests.

**What it is not.** Not a framework, not a runtime, not a memory database, not a model.
It is the prompt-and-policy layer: roughly 28 small ES modules and ~1,510 tests.

## 一、这个引擎解决的具体问题

陪聊类应用最常被吐槽的不是"模型不够聪明"，而是下面这些**结构性毛病**。
每一条在这个仓库里都有对应的实现，也都有对应的测试。

| 毛病 | 症状 | 这里的做法 |
|---|---|---|
| **失忆** | "啊？你说过吗""我们才刚认识吧" | 记忆块放在提示词**最前面**（模型对开头最敏感）；关键词 IDF 检索翻出几百条以前的对话 |
| **记忆不真实** | 五年前的事连"她那天穿什么"都记得 | 遗忘曲线 + **纯细节封顶**：事情记得住，细节会模糊，而且要求她**照实说记不清、不许编** |
| **感情不升温** | 聊三个月还是陌生人语气 | 好感度分 5 档，每档写清"该怎么表现"；聊天微调（+0.4/句这种量级）；久不联系会淡 |
| **关系串味** | 设成"同事"却说着"想你" | 关系=**身份**（写死、不许动摇）／好感度=**温度**（会变），两个正交的轴 |
| **时间错乱** | 晚上十点说"明天下午送你",她急着催你快出发 | 注入虚拟时间；他说的时间词**先替她算好还剩多久**，明确写"现在还早，不用着急" |
| **人设漂移** | 20 岁设计生张口"我当年带团队做全案" | 知识储备按**年龄 + 职业**分档（学生版/工作版），12 个知识域 |
| **不懂装懂 / 冷场** | 要么硬答专业问题，要么一句"这我不懂"把人堵回去 | 同行才聊专业；不同行承认不懂**但必须带上跟情境相称的情绪**，并且 ⭐「不懂专业 ≠ 不懂他」 |
| **情绪平面** | 无论什么情况都是同一个温度 | 情绪强度 → 执念（≥7 分不受遗忘曲线影响）+ 情绪表达规则（开心的语气词怎么落字面上） |
| **情绪看不见** | 她生气了你看不出来，只能猜 | **实时情绪**：顶部一条"生气 8%　心动 15%"，可多个同时显示；表情/颜文字也跟情绪联动 |
| **应声虫** | "好的""我理解你的感受""你可以试试…" | 反顺从规则；共情优先于给建议；**人本主义三条件**（共情/真诚/积极关注） |
| **一上来就掏心掏肺** | 好感度这根轴完全没意义 | 积极关注**分档**：低好感是"有条件关注"（好是要挣的），高好感才是"无条件积极关注" |
| **只会一个人设** | 想要个毒舌同事换换口味，得把现在这个删了 | **多好友**：每个好友独立的记忆/人设/好感度/情绪；我的资料全局共享、改一次全都看得到 |
| **场景写不进聊天** | 想让"她推门进来"发生，只能骗一句台词 | 独立的**旁白输入框**（环境/动作/内心），和发送键共用；她自己的（）也拆成同一种框、画在她那一侧（谁写的看左右，不看颜色） |

> 这些不是"提示词里多写几句"能解决的，它们互相打架。
> 比如"关系写死"和"温度会变"就会冲突，所以必须先想清楚哪些是身份、哪些是温度。

## 二、与同类项目的区别

先划清一件事：**这个仓库不是它们的竞品，它站在另一层。**
那几个项目做的是**运行时 / 框架**（角色引擎、状态机、记忆后端、服务端进程）；
这个仓库做的是**提示词与策略层** —— "她该记得什么、她该懂什么、她的情绪该怎么变"，
以及把这些写成**能跑、有测试、可以整层抄走**的形态。

| 项目 | 它擅长什么 | 和这个项目的区别 |
|---|---|---|
| [**Shikigami-Protocol**](https://github.com/Shikigami-Lab/Shikigami-Protocol) | 本地优先的角色**运行时框架**：情绪 × 精力 × 好感三个状态机、内置记忆管线（事实 / 向量 / 日摘要）、后台反思、沉默后主动开口。Electron/Vue + FastAPI，AGPL-3.0 | 它是**应用 / 框架**——想跑起来得接受它的技术栈和常驻进程；**这里是提示词与策略层**，纯浏览器、零运行时依赖、无构建步骤，可以只抄其中一层（比如只要遗忘曲线，就那 173 行） |
| [**alive-ai**](https://www.npmjs.com/package/alive-ai) | **多类记忆的拟生架构**：working / episodic / semantic / emotional / autobiographical，外加 dream 与 shadow memory，主打"数字神经系统" | 它把重点放在**记忆的类别划分**上；这个项目的重点在**记忆的四种失效方式**（写错 / 该忘没忘 / 该记没记 / 想不起来）以及**知识边界**——角色知道自己该懂什么，不懂时不装懂、但也不冷场 |
| [**feltstate**](https://github.com/Morephine/feltstate) | **情感与记忆的持久化引擎**（Python 库）：5W1H 事实衰减、执念、双时态查询、哈希链审计、崩溃安全的级联删除 | 它的记忆生命周期**比这个项目成熟得多**（540 项测试、`gc` 判定与回收执行分离）。差别在**形态与场景**：它为"一个 agent 调用一个库"设计，值得长跑、值得审计；这里是**静态页面里跑、无处部署后端**，代价是"删除"只能是清 localStorage |
| **这个仓库** | **角色该表现得知道什么**：知识边界（不懂 ≠ 冷场）、关系身份与温度双轴、三种时间尺度分开的情绪，以及把这些意图**锁进 1679 项断言** | —— |

**一句话概括差异**：它们回答"记忆和情绪**怎么存**"，
这个仓库回答"**角色该表现得知道什么、以及不懂的时候怎么不伤人**"。
后者主要靠提示词，而提示词最容易失效、也最少被认真测试 —— 所以这里把测试压在它上面。

> 对比基于它们的公开文档，我没有通读源码。如果描述有偏差，欢迎指出。

## 三、架构：越往下越纯

**核心设计原则：`app.js` 以下的所有模块都不碰 DOM，也不碰全局状态。**
状态和副作用全部集中在最上面那一层 —— 这是它们能被单独 import 和测试的前提。

```
                        ┌──────────────────────────────────────────┐
                        │  app.js        状态 · 界面 · 事件 · 编排   │
                        │  （唯一持有 state，唯一碰 DOM）           │
                        └──┬────────┬────────┬────────┬─────────────┘
                           │        │        │        │
         ┌─────────────────┘        │        │        └──────────────┐
         ▼                          ▼        ▼                       ▼
 ┌────────────────┐      ┌──────────────┐ ┌──────────┐   ┌────────────────────┐
 │ persona.js     │      │ storage.js   │ │ mood.js  │   │ friend-ui.js       │
 │ 把下面这些拼成  │      │ localStorage │ │ 实时情绪  │   │ 消息/好友/我       │
 │ 系统提示词      │      │ + 存盘前整理  │ │ 衰减+合并 │   │ 加好友/我的资料     │
 └─┬───┬───┬───┬──┘      └──────┬───────┘ └──────────┘   └─────┬──────────────┘
   │   │   │   │                │                              │
   ▼   ▼   ▼   ▼                ▼                              ▼
┌────┐┌────┐┌────┐┌──────────┐┌────────┐            ┌─────────────────────┐
│zodiac││affec││rela││professio││memory  │            │ personas.js         │
│星座 ││好感度││关系 ││职业知识  ││遗忘曲线 │            │ 多好友：索引/路由/   │
└────┘└──┬─┘└──┬─┘└─────────┘└───┬────┘            │ 老数据兼容          │
         │     ▼                  │                 └──────────┬──────────┘
         │ ┌──────────────┐       │                            ▼
         │ │relation-views│       │                 ┌─────────────────────┐
         │ │ 关系视角文案  │       │                 │ presets.js 预置人格  │
         │ └──────────────┘       │                 │ me.js 我的资料(全局) │
         │                        │                 └─────────────────────┘
         ▼                        ▼
 ┌────────────────────────┐  ┌─────────────────────┐
 │  memory-io.js          │─▶│  recall.js          │
 │  记忆读写/检索/导入      │  │  2/3-gram + IDF     │
 └────────────────────────┘  └─────────────────────┘
         ▲
 ┌───────┴────────┐
 │  emotion.js    │  情绪强度打分（≥7 = 执念）
 └────────────────┘

  另外几个谁都不依赖的小模块：
    format.js   文本格式化（HTML 转义闸门 / 时间显示 / 时长说法）
    search.js   搜聊天记录（纯子串，给人用的，和 recall.js 的模糊匹配相反）
    habits.js   相处习惯（反复做过的动作，别再给"第一次"的反应）
    api.js / providers.js / config.js
    native.js   手机本地推理桥接（只在安卓版里真正生效）
```

> ⚠️ 只有两个**例外**：`friend-ui.js`（消息页/好友页/我/加好友）和 `ending-ui.js`
> （终局确认、删档、删好友）要碰 DOM，也要 app.js 的一大堆状态。
> 做成"参数传入"的纯模块会让调用点没法看（要传二十个东西），
> 所以它们用**工厂模式** —— app.js 启动时把依赖一次性交进去。
> 别把这个模式复制到别处：别的模块都该是纯的。

### 数据流

```
respond()
  ├─ 虚拟时钟算"现在几点"                    ← persona.describeTime
  ├─ 从旧记录里翻相关的话                     ← memory-io.recallOldMessages → recall.js
  ├─ 按遗忘曲线淘汰 + 钉住手动条目             ← storage.decayProfileFacts / hoistManualEntries
  ├─ 拼系统提示词                            ← persona.buildSystemPrompt
  │    ├─ 关于他的记忆 / 他是谁（我的固定档案）
  │    ├─ 你此刻的心情（实时情绪）
  │    ├─ 关系身份 / 此刻温度 / 人本主义
  │    └─ 她懂什么（年龄+职业+同行判断）/ 星座 / 场景 / 相处习惯
  ├─ 发给模型（云端 api.js 或本地 native.js）
  ▼
她回了一段话
  ├─ 摘掉隐藏的 [[记忆]] 块                   ← memory-io.parseMemoryBlock
  ├─ 摘掉隐藏的 [[情绪]] 块                   ← mood.parseMoodBlock
  ├─ 写进记忆 + 打情绪强度分                   ← memory-io.applyMemory（用 emotion.js）
  ├─ 情绪并进当前心情（先衰减再加）             ← mood.blend
  ├─ 好感度微调                              ← affection.drift
  └─ 存盘（先整理一遍）                       ← storage.saveProfile / writeChat
```

## 四、核心设计取舍

> 每一节都是一个**具体的失效方式**，以及为了堵住它付的代价。
> 标题只用来说明这节讲什么，理由和踩过的坑都在正文里。

### 1. 记忆为什么分三层：写入、淡忘、检索的失效方式完全不同

```
写入（memory-io.applyMemory）  一件事该不该记、记多重   ← 情绪强度打分
淡忘（memory.js + storage）    记下来之后会不会忘      ← 复习次数 / 半衰期
检索（memory-io + recall.js）  什么时候被想起来        ← 2/3-gram + IDF
```

分开是因为它们的**失效方式完全不同**：写入错了会记进假信息；
淡忘错了会"该忘的没忘"或"不该忘的忘了"；检索错了是"她明明知道却想不起来"。
混在一起时这三种 bug 长得一模一样，只能靠猜。

**纯细节封顶**是这里面最反直觉的一条：情绪强度再高，
只要条目里只有"几点""穿什么""在哪"，就**不给它执念资格** ——
让它像普通记忆一样淡掉。因为真人就是这样：事情记得，细节记不清。
而且明确要求她**照实说记不清，绝对不许编细节** ——
编出来的细节一旦对不上，比老实说"我忘了"更伤人。

但这一层还有个更硬的失效方式，是用户实测撞出来的：
**"中午带她去开会，晚上她就忘了"** —— 完整上下文只带最近 200 条、要点压缩按**长度**
挑前 8 条（"随便聊聊今天天气还行"比"中午带你去公司开个会"还长，于是闲聊赢、
事件被丢）、检索又要求他晚上那句话正好命中"开会"。
现在窗口放宽到 400 条，要点改成**按时间分段 + 事件词加权**，
再加一块**「今天你们已经做过的事」**：把掉出窗口的当天消息按时间列成事件线，
不需要命中关键词。**记忆最靠不住的一层不是"忘"，是"取舍"** ——
挑错了，那件事就再也不会被想起来。

### 2. 关系和好感度必须是两个轴

一开始把两者写在同一段提示词里，结果它们**互相打架**：
好感度低时写"客气、有距离"，关系那块却写着"恋人"，模型直接演崩。

拆成正交的两个轴之后：
- **身份**写死、不许动摇（生气冷战也不降级，记录里有旧关系以最新为准）
- **温度**会变，但再低也不会低过身份（恋人冷淡 ≠ 恋人变陌生人）

"她认为我们的关系"这句话也是同理：原来 5 个通用模板套所有关系，
套到"夫妻"上会读出"你们早就不只是夫妻了"——**这句话本身就是错的**。
现在 15 种关系 × 5 个档位各写各的。

### 3. 积极关注必须分档

分档的理由很实际：**低好感那档一旦写暖，整个好感度系统就白做了**。

罗杰斯的三个核心条件里，**共情**和**真诚**任何档位都成立（这是"像真人"的底线）。
但**积极关注**必须分档，否则好感度这根轴就没意义了：

| 好感度 | 积极关注 |
|---|---|
| < 40 | **有条件**：你的好是**要挣的**，他敷衍你就收回来 |
| 40–69 | 在变松，但还没打算惯着他 |
| ≥ 70 | **无条件**：不管他做了什么，都不否定他**这个人** |

写的时候最容易犯的错是**把低好感那档写暖** ——
那样她会一上来就掏心掏肺，整个好感度系统就白做了。

### 4. 她感知的"现在"不跟现实走

```js
const now = () => Date.now() + (Number(state.config.clockOffset) || 0);
```

全系统（时间描述、场景演变、消息时间戳、记忆衰减）都用这一个 `now()`。
看一场两小时的电影就点「+2 小时」，她就**真的觉得过了两小时**；
也可以直接选"跳到某年某月某日几点"。

配套的坑：**拨时间不许重画整个聊天区**（聊到几百条时那一步肉眼可见地卡），
只刷新时钟文字和时间分隔条的文案 —— 测试里直接断言
"拨完之后聊天区的 DOM 节点还是同一个"。

第二个坑更隐蔽：他把时钟拨到早上八点，她还是说"快十一点了"。两层原因 ——
提示词从没要求"他问时间就照实念"（模型凭感觉估了一个数），
而场景描述里若写着"晚上"（人设页写死的初始环境不随时间演变），模型就挑了个自洽的说法。
现在时间那一行被标成**唯一权威**（比场景描述更硬），冲突时直接点破，
并额外给一句**可以照抄**的口语答案 —— 让模型抄，比让它自己算可靠得多。

### 5. 她懂的必须跟年龄和职业对得上

只写一句"你是学视觉传达的大二学生"是不够的：她一聊到画图就会冒出
职业设计师的口气（"我当年带团队做全案"），人设当场就假了。

所以知识储备按 **12 个知识域 × 学生版/工作版** 给，
年龄只用来在两者之间选（20 岁的程序员也算工作版）。

**同行 / 不同行**是另一个轴：
- 同行 → 能聊到一块去（吐槽 / 请教 / 有点小较劲三种自然反应）
- 不同行 → 只聊自己那摊，承认不懂

这一块最容易做坏成"不懂你的专业 = 不懂你"，
所以里面明确写了：情绪要跟情境相称（他兴奋→好奇、抱怨→共情、
泄气→**不夸他的专业，夸他这个人**、较真→自嘲），
⭐「不懂专业不等于不懂他」，而且**不许每句都"我不懂"**。

### 6. 检索用 IDF 而不是向量

手机端跑 embedding 要额外下模型、额外算力。
2/3-gram + IDF 这一档对"做饭""加班""猫""项目"这类具体话题已经够用，
而且**零成本、零依赖**。中文不用词典也能切。

代价是**单个汉字搜不出来**（2-gram 起步）—— 这是刻意的取舍，写在代码注释里了。

### 7. 多好友让默认角色继续用扁平 key

从"一个人"变成"通讯录"时，最直觉的做法是把数据全搬到 `personas/<id>/...`。
但那等于**把存储格式重写一遍**：老用户的存档要迁移、上百处测试要改，
任何一处漏了就是"升级后聊天记录没了"。

所以选了另一条路：**默认好友（`id = default`，就是默认那个角色）
继续用原来那三个扁平 key**。

```
default  → xiaoyu.{config,chat,profile}.v1          ← 老地方，零迁移
新好友    → xiaoyu.persona.<id>.{config,chat,profile}.v1
```

老用户零迁移、老行为不动，**多好友是纯增量**。
代价是"默认好友是个特例"—— 但这件事被收在 `personas.js` 的 `keysFor()`
一个函数里，别的地方不用知道。

**每个好友各存各的**：记忆、人设、好感度、场景、聊天记录互不干涉。
**只有内置时间是全局共享的** —— 它本来就是"世界时间"，不是某个人的。
**我的资料也是全局一份**（`me.js`）：改一次所有好友都生效，
不然换个职业要改十几次，迟早不一致。

### 8. 三个"情绪"必须分开

这个项目里有两个模块名带"情绪"，加上好感度，一共三个轴，
**它们的时间尺度差了三个数量级**（几分钟 / 几个月 / 永久），混在一起会出大问题：

| | 是什么 | 时间尺度 |
|---|---|---|
| **情绪强度**（`emotion.js`） | 一件事有多重（≥7 算执念，影响会不会被忘掉） | 永久 |
| **好感度**（`affection.js`） | 她对你整体的温度 | 几个月 |
| **实时情绪**（`mood.js`） | 她**此刻**的心情 | 几分钟 |

关键的一条：**实时情绪只影响她怎么说话，绝不去改好感度。**
否则"她刚才生气了"会变成永久扣分 —— 聊几句就掉到底，好感度那根轴就废了。

情绪从她回复里带的隐藏块 `[[情绪]]{"anger":8}` 来，
再加一层本地兜底（他那句话的冷暖）。两个都过 `blend()`：
**先按半衰期衰减、再取较大值合并** —— 所以她会"又气又舍不得"，
而不是后一个情绪把前一个覆盖掉。低于 3% 就当没有了
（免得界面上一直挂着"1%"）。

### 9. 旁白不做成一种语气，做成一种**位置**

括号旁白这件事在这个项目里反转了三次，值得记下来，因为**最后那次不是审美问题，
是定位问题**：

- 一开始**禁止**她写（模型爱偷偷写、写了又没下文）
- 后来改成"可以写，但后面必须跟真话"（实测禁不住）
- 再后来用户要自己写旁白（独立输入框，和发送键共用），于是又**禁止**她写，
  理由是"两边会撞在一起，而且她的括号还得单独占一个气泡"
- **现在是放开**：她写的内容（动作、神态、环境、心里话）本来就是对的，
  错的是把它和台词塞进同一个气泡。**禁了两轮，模型照写。**

所以最终的分工不是"谁来写"，而是**位置**：

| | 台词 | 旁白 |
|---|---|---|
| 我 | 右边 | 右边 |
| 她 | 左边 | 左边 |

同为灰色虚线小框、都没有头像（旁白是场景说明，不是谁说的话），
**靠左右分边表示是谁写的**。于是她写括号从"要堵的漏洞"变成了要的行为 ——
`src/narration.js` 把她的回复按（）拆成两种条目（顺序不变：
"我没事（笑）真的" → 台词 / 旁白 / 台词），`app.js` 只负责接线。

三条边界（都被测试钉着）：半角括号里得有中文才算旁白（`(lol)`、`(๑•̀ㅂ•́)و` 留在台词里）；
**不跨行配对**（否则整段聊天会被一个括号吃掉）；`（空行）`/`（换行）` 不当旁白 ——
那是模型把分段标记写成了文字，得留给拆条逻辑还原成真换行（踩过：一句话被切成三个框）。

旁白**不占"连发条数"**：它是舞台说明，不是她发的消息。

**旁白和「思考」是两件事**（这一条是用户后来纠正的）：旁白是**看得见的** ——
动作、神态、环境，而且**可以没有**（这一轮没什么动作就别硬凑）；
「思考」是**看不见的** —— 对**下一句话**的内心独白，折叠起来、点开才看得到。
界面上的顺序也是这个逻辑：**思考 → 旁白 → 台词**，
读起来就是"心里怎么想 → 手上怎么做 → 嘴上怎么说"。
我一开始没把这层分工写清，模型就把思考写成了动作（"把手机翻过来扣在桌上"），
两个功能撞在一起，等于白做。
它和**情绪**也必须是两件事（用户专门强调："思考指的是讲下一句话时的内心想法，
而不是有情绪才有思考"）。我一度把两者捆成"每次回复都要带的两块"——
那会让她以为"有情绪才有思考"。现在是两段独立的要求：
**内心每一轮都要有**（平平淡淡也在想事），**情绪平淡就写空**（`[[情绪]]{}`）。

但"允许她写"之后冒出了第三个问题：**她开始写空动作** ——
用户的原话是「我问几点了，为什么会顿住呢，为什么不可以是，抬头看了一眼呢」。
这类词（顿住 / 沉默 / 脸红）只是"她有个反应"，既看不见也听不到，
等于把旁白这个功能浪费掉了。

所以 `narration.js` 里有一份**空动作黑名单**，一份词表两处用：
提示词里的反面例子，和"最近写过的旁白"里的点名提醒。
判断标准也写进了提示词 —— **这句话能不能拍出来？**
能看见谁在动、动的是什么、朝哪个方向 → 合格；只有一个情绪词 → 重写。
最后加一句约束把旁白拉回它的本职：**动作要接得上他刚说的那句话**
（他在问时间 → 你看钟 / 摸手机；他在哄你 → 你把脸埋进枕头）。

### 10. 旁白不能代替回答

用户实测的原话：「比如我问几点了，她出一个旁白：（抬头看墙上的钟）。然后就没有下文了，
应该是她出一个旁白，然后接着告诉我几点了，不然我还得再问一遍。」

这条坑的根子不在于"旁白写多了"，而在于**模型把"做了一个看钟的动作"当成了"回答"**——
在它那边这一轮已经交代过了。所以旁白越生动，这个坑越明显。

修法是**两层**。提示词里新加一块【他在等你的回答】——按"他会怎么问"列了七类情景
（问时间 / 状态 / 你的事 / 你的判断 / 让你做件事 / 你的心情 / 一次问两件事），
每类都写明"答案必须出现在**台词**里"，把"（抬头看墙上的钟）就没了"当反面例子
摆在最显眼处，并要求发之前自检一句"他问的那件事，我在台词里回答了吗"。
代码里再加一道闸（`app.js` 的 `askForWords`）：**整轮都是旁白**时，
自动再要一次"只要台词"的短请求（`max_tokens: 120`），把欠的那句话补上、拼在动作后面。

这道闸能上线的三条自我约束：只在整轮旁白时触发（正常回复一次请求都不会多发，有测试钉着）、
一轮最多补一次且补回来还是旁白就认了（**绝不死循环**）、补的过程失败就当没发生。

顺带说一句同一轮的另一个坑：**性格标签在模型那里会被读成"音量键"**。
选了"温柔 + 慢热 + 内向"的人设，她会一路演成满屏"嗯""哦""好"——
用户的原话是"温柔标签不代表沉默寡言"。所以每个标签后面都补了"但不等于…"
（温柔是语气不是音量、内向对熟人话很多、慢热"你们已经熟了"），
并单独加了一块【性格是配比，不是音量键】：标签只改语气，不改话量。

### 11. "忘记一切"是删好友，不是清空记录

用户写的旁白如果是「很多年后，我们一起老去，最后都离开了这个世界」，
那在剧情上等于**给这段关系画了句号**。直接删，他可能只是一时入戏；
不管，她会带着"我们都已经死了"继续跟他聊晚饭吃什么 —— 所以**停下来问一句**：
两轮确认（"是否忘记你们的一切？"→"再确认一次"）。
按钮配色也是内容的一部分：**"是"用灰色、"否 / 我还没想好"用绿色** ——
危险的那个不能长得像推荐选项。任何一步选否，就把刚才那段剧情**圆成一场梦**
（"你们都睡着了，做了一个好梦，白天醒来又是美好的一天"），而不是假装没发生。

两个被这个功能逼出来的决定：

- **"忘记一切"= 连好友一起删**（他明确要求的）。所以会出现**"一个好友都没有"**
  这个状态 —— 界面必须给下一步（"请添加一个好友"），否则就是一个空壳。
  索引里用 `noDefault` 记住"默认好友是他删的"，不然下次一修索引它又回来了。
- **只在旁白里判，词表都是成句的**。台词里说"我要跟你走一辈子"是表白；
  "笑死我了""想死你了"在中文里全是夸张用法 —— 误判会突然弹窗打断正常聊天，
  比漏判难受得多。**宁可漏，不可误。**
  这条还被用户纠正过一次：我一度把"一起老去""白头到老""很多年后"也算进去，
  于是「（我们一起走了出去）」都会弹窗。现在**只认明确的死亡语义** ——
  成词（去世 / 离世 / 葬礼 / 墓前…），或者单个"死"字必须有人称、
  或"一起 / 双双 / 都"紧挨着（`她死了` ✓、`累死了` ✗）。

## 五、跑起来

```bash
npm install        # 只为测试装 jsdom，运行时零依赖
npm run dev        # → http://localhost:8090
```

打开后：填 API Key → 开始聊。
**模型固定在 `deepseek-flash`**（陪聊要的是快和便宜，切换模型对"她像不像个人"没有帮助，
反而多一个能调坏的地方 —— 所以设置页只有 Key 和测试连接）。
Key 只存在你自己的浏览器 localStorage 里，不会上传到任何地方。

想完全离线：安卓版可以把 llama.cpp 放进手机里跑（`src/native.js` 是桥接层，
需要自己配 Capacitor 工程）；`src/providers.js` 里也还留着本地服务的预置，
想放开的话从 `providers.js` + 设置页那两处入手。

### 测试是怎么跑起来的

`boot.mjs` + `inline.mjs` 把前端模块**内联进 jsdom**，并注入真实的 `styles.css` ——
不注入的话 `getComputedStyle` 只能看到浏览器默认样式，
"被 `hidden` 的元素是不是真的看不见"这类断言全是假绿。

`test-modules.mjs` 是另一层：它在 **node 里（没有 DOM）直接 import 每个模块**。
这是"真的解耦了"的唯一硬证据 —— 只经过 `app.js` 的话，
模块里偷偷用了全局 `state` 或 `document` 也发现不了。

断言的是**场景**，不是函数：比如"改了名字后她自我介绍会不会跟着更新"、
"长期不联系感情会不会降温"、"晚上十点说'明天下午送你'她会不会催你快出发"、
"她只发一个动作时会不会把该回答的答案补上"。
所以改提示词或改界面时，先跑一遍就知道有没有踩坏别的地方。
